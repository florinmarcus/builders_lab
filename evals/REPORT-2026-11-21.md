# Retrieval and answer quality: status report, 21 Nov 2026

Sources: `evals/results/*.summary.json`, `evals/experiments/`, `corpus/OVERNIGHT-REPORT.md`, `corpus/OVERNIGHT-PLAN.md`.

**Main caveat.** These numbers were measured on the overnight staging corpus (`corpus_next`), not on live. Live now has the
12-document corpus, with keyword search on and no relevance cut-off. That exact setup was never measured end to end.

## 1. Golden set

- **Size:** 407 questions in v2. v1 had 412: 4 were dropped and 1 removed.
- **How it was made:** six role-played users wrote the questions in builders' wording. A separate pass labelled
  them, and an adversarial pass reviewed them. The holdout was fixed before any run.
- **Roles:** asbestos 66, building control 70, fire safety 68, housing repairs 64, money 70, site safety 69.
- **Kinds:** answerable 284, negative (false premise) 46, out of scope 47, underspecified 30.
- **Shape:** 312 questions need more than one rule; 335 are specific and 72 are broad.
- **Label confidence:** 351 high, 51 medium, 5 low.
- **Each question has:** a reference answer, the clauses it cites, and the expected sections. 352 questions have
  expected sections: 299 dev and 53 holdout.
- **Splits used:** the retrieval runs used v1 (273 labelled dev questions). The judge used 342 dev questions.
  **The holdout has never been run.**
- **Gaps:**
  - One question per exchange only. No multi-turn scenarios.
  - Questions and labels were written by models, not real builders.

## 2. Retrieval

**Pipeline:** Titan v2 embeddings, then pgvector nearest chunks, plus optional BM25 keyword search (merged). Then
Amazon Rerank v1, then the top 5.

**Metrics:**
- **Recall@k** is a hit rate: 1 if any expected section, or a part of it, is in the top k.
- MRR@5 and nDCG@5 are also reported. nDCG grades the first expected section 2 and the others 1.
- **all@5** counts a hit only if every expected section is in the top 5.

**Strict and pooled:**
- **Strict:** only the sections the labeller listed count as correct.
- **Pooled:** a section that search found and the labeller did not list also counts, if a separate judge model
  read it and confirmed it answers the question. This is TREC-style pooling (`evals/golden/pool_judge.py`).
- Why pooling exists: regulations often say the same thing in two places, so strict recall under-counts.
- The risk: a model judge decides what counts, so pooled recall is an upper estimate.

**Dev results, 273 questions, staging corpus, no relevance cut-off:**

| Setup | R@5 strict | R@5 pooled | R@50 pooled |
|---|---|---|---|
| E1 vector + rerank | 0.65 | 0.75 | 0.84 |
| E2 hybrid | 0.67 | 0.78 | 0.87 |
| E5 hybrid + 2 extra queries, merged | 0.70 | 0.82 | 0.93 |

- With the old live cut-off of 0.05, E1 R@5 drops to 0.32. (The `recall@5` field in the summary files is at this
  cut-off.)
- No gain from: E4 (Cohere rerank), E6 (rerank using the extra queries), E7 (top 100).
- Latency p50: hybrid about 1.9 s, E5 about 4.9 s.
- The target of R@5 ≥ 0.90 was not met.

**Full corpus (186 sources, 40,075 chunks), 21 Nov morning, 100 dev questions:**
- R@5 0.68, against 0.27 for the live 12-document corpus.
- R@50 0.83, against 0.36.
- There is no result file for this run, only the log line in `corpus/OVERNIGHT-PLAN.md`.

## 3. What was tried to raise recall, and what was not

**Tried (only search methods):**
- hybrid keyword search
- extra queries written by the specialist (E3, E5)
- a different reranker (E4)
- reranking using the queries (E6)
- more candidates (E7)
- dropping the relevance cut-off

**Not tried:**
- **A systematic look at the misses.** The only note: "remaining misses are sibling sections under the same
  heading and documents not yet loaded".
  - No sorting of misses by cause (parse, chunk, embedding, ranking, label, missing document).
  - No per-document or per-chunk-type breakdown.
- **Chunking experiments.** One strategy only: one chunk per section, paragraph or table row, with splits above
  about 2,500 characters. No tests of size, overlap, adding the parent heading or merging sibling sections.
- **Parser quality against recall.** Parsers have validation checks, but nobody measured how parse errors affect
  recall.

## 4. LLM as a judge

**Setup:**
- Haiku 4.5 on Bedrock writes the answer from the top 5 passages.
- gpt-oss-120b on Bedrock judges it, at temperature 0.

**Criteria, each scored 1-5 with the reason first:**
- **Correctness** against the reference answer. "NOT IN SOURCES" on an answerable question scores 2 at most.
- **Grounding:** every claim is supported by a cited passage.
- **Completeness:** the main points of the reference answer are covered.
- **Pass** means correctness ≥ 4 and grounding ≥ 4.

**Results, 342 dev questions:**

| | Old live setup | Hybrid, no cut-off | E5 |
|---|---|---|---|
| Pass, all | 0.31 | 0.57 | 0.58 |
| Correctness / grounding / completeness | 2.7 / 3.2 / 2.4 | 3.7 / 4.1 / 3.1 | 3.7 / 4.2 / 3.1 |
| Answerable pass | 0.22 | 0.52 | 0.50 |
| Answerable "not in sources" | 0.58 | 0.07 | 0.09 |
| False premise pass | 0.44 | 0.66 | 0.76 |
| Out of scope pass | 0.64 | 0.77 | 0.85 |
| Underspecified pass | 0.52 | 0.67 | 0.57 |

**Significance (McNemar):**
- Old live setup to hybrid: χ² = 70 (103 questions gained, 13 lost).
- Hybrid to E5: χ² = 0.02 (no difference).

**Weaknesses:**
- The judge is not a Claude model, and the answer model is not the product model.
- One judge, with no human calibration.
- It tests the search alone, not the real flow (plugin, specialist, `verify_answer`).
- No trace of the tool calls behind each answer.

## 5. Overfitting

- All tuning used dev. The holdout is untouched, which is good.
- Risks:
  - many configurations were compared on the same dev set
  - pooled labels come from a model
  - the labels were written by the same model family that later answers
- Rule from now on:
  - decide changes on dev
  - check on holdout once per milestone
  - never tune on holdout
  - report the confidence interval: ±0.06 at n = 273 and p = 0.7 (Wilson, 95%)

## 6. Owner's direction (Florin, 21 Nov)

- No LLM on AWS. Only the embedder and the reranker stay on Bedrock.
- Judges run locally in Claude Code: Opus and Sonnet (or Fable and Opus), on the user's plan.
- Add multi-turn scenarios to the golden set.
- Look at the misses systematically before tuning: parse, chunk, rank, label.
- Trace every tool call in a judged run: server logs and retrieval logs.
- No overfitting.
