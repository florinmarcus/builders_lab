# Measure the noise before trusting the gain

Your current eval kit has the right parts: a golden set, retrieval metrics, two judges, paired tests, repeats, a held-out split and a gate. What it lacks is the data-science layer that says how much any one number can be trusted. Four gaps matter most. First, a 300-question set can reliably detect a change of about **5 accuracy points**, not 2, unless you use paired analysis, repeats and clustering correctly. Second, an LLM judge is a classifier. It needs a frozen, labelled test set and a confusion matrix (true positive rate, true negative rate, kappa). Its raw pass rate should then be corrected for its known errors. Third, evals should grow out of error analysis, meaning reading traces, naming failure modes and counting them, not out of generic 1-5 quality scores. Fourth, retrieval and graph-versus-vector decisions should be made per question type, with labels that survive re-chunking, token budgets matched between systems, and judges debiased. Independent studies show that most headline GraphRAG wins shrink or vanish under those controls. The rest of this report explains each discipline, maps what you likely do now to the rigorous version, and ends with questions for a grilling session. It is theory and published evidence, not a description of any one system.

## Error analysis decides what to measure, before any metric

The practitioners who write most about LLM evals, Hamel Husain and Shreya Shankar, start with qualitative research, not dashboards. You read real (or synthetic) traces. You write free-text notes on the **first failure** in each trace, because one upstream error causes many downstream symptoms. This is called open coding. You then group the notes into about **5-10 failure modes** (axial coding), count them, and continue until new traces stop showing new modes ("theoretical saturation") ([Husain & Shankar FAQ](https://hamel.dev/blog/posts/evals-faq/why-is-error-analysis-so-important-in-llm-evals-and-how-is-it-performed.html)). The suggested volume is at least **100 diverse traces**, read by one trusted domain expert (a "benevolent dictator"), not outsourced. In production, read 100+ fresh traces every 2-4 weeks and 10-20 outliers each week ([Evals FAQ](https://hamel.dev/blog/posts/evals-faq/)). Label at least 30 traces yourself before you let an AI suggest labels, or its early guesses will bias you. The authors say they spend **60-80% of development time** on error analysis and evaluation. In one worked case, three failure types made up over 60% of problems. Targeted tests then lifted success on the worst one from 33% to 95% ([Field Guide](https://hamel.dev/blog/posts/field-guide/)). Nobody gives a numeric rule for when saturation is reached. It is a judgement call.

The output of error analysis is a counted, ranked list of failure modes. Each mode then gets one of four treatments. If it is a specification gap (the prompt never said what you wanted), fix the prompt and move on; no eval needed. If it keeps coming back and a rule can check it, write a **code assertion** and run it in CI ("If a failure can be verified with code, always use a code-based eval") ([Pragmatic Engineer](https://newsletter.pragmaticengineer.com/p/evals)). If it keeps coming back and needs judgement, build a **separate LLM judge for that one failure mode** and validate it against expert labels. If it is rare and cheap to tolerate, note it and do nothing. Husain advises against writing evals for failures you imagine rather than observe, and against keeping evals that always pass: "If you're passing 100% of your evals, you're likely not challenging your system enough" ([Evals FAQ](https://hamel.dev/blog/posts/evals-faq/)). Anthropic makes the same split between capability evals, which start low and are "a hill to climb", and regression evals, which sit near 100%. A capability task that passes moves into the regression set ([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).

### Binary verdicts per failure mode beat one 1-5 score

The practitioner consensus is binary pass/fail per criterion, with a written critique, combined by simple rules such as "pass only if all pass". The case against 1-5: the line between a 3 and a 4 is subjective, annotators drift to the middle, and Likert scales need larger samples to detect differences ([Evals FAQ](https://hamel.dev/blog/posts/evals-faq/); [Eugene Yan](https://eugeneyan.com/writing/product-evals/)). Arize found that numeric judge scores bunched into narrow bands, varied across runs and were not comparable across judges, while binary labels were stable ([Arize](https://arize.com/blog/testing-binary-vs-score-llm-evals-on-the-latest-models/)). The evidence is not one-sided. A January 2026 preprint found a 0-5 scale gave the best human-LLM agreement on some tasks ([arXiv 2601.03444](https://arxiv.org/html/2601.03444v1)). The practical reading is that your 1-5 score with a pass threshold is already a binary classifier at that threshold, so validate it as one (see the judge section). If you want graded progress, use binary sub-checks such as "4 of 5 expected facts present".

### Criteria drift means labels and rubrics are versioned artefacts

Shankar's "Who Validates the Validators?" study named **criteria drift**: "users need criteria to grade outputs, but grading outputs helps users define criteria." Practitioners added criteria after seeing new failures, loosened rules ("all" became "most"), and sometimes gave a grade only to stay consistent with earlier grades ([Shankar et al. 2024](https://arxiv.org/html/2404.12272v1)). The study is small (9 people), but the lesson is general. Gold labels and judge prompts change as your own standard settles. When a criterion changes, re-label the affected examples. Expect early judge agreement numbers to move.

### Synthetic questions need dimensions, not free generation

When real traffic is thin, define the dimensions along which inputs vary (feature, scenario, persona, complexity). Hand-write about 20 tuples, let an LLM extend them, then turn each tuple into a natural question in a separate prompt. Asking an LLM for questions directly "tends toward generic outputs and misses rare scenarios" ([Evals FAQ](https://hamel.dev/blog/posts/evals-faq/)). Generate inputs, not expected answers. Check that each question really triggers its scenario, and replace synthetic items with real ones as they arrive ([Field Guide](https://hamel.dev/blog/posts/field-guide/)). For agents, Anthropic suggests starting with 20-50 tasks taken from real failures. Each task should be clear enough that two experts would agree on it, and the set should test both where a behaviour should happen and where it should not ([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). For multi-step agents, a **transition failure matrix** (last successful step against first failing step) shows where agents break ([Evals FAQ](https://hamel.dev/blog/posts/evals-faq/)).

## A 300-question set detects about five points, not two

The core statistical fact is simple. The standard error (SE) of a pass rate p on n independent questions is sqrt(p(1-p)/n). Evan Miller's "Adding Error Bars to Evals" (Anthropic, 2024) asks that every eval score be reported with its SE and n ([Miller 2024](https://arxiv.org/html/2411.00640v1)). Worked from that formula, at 85% the SE is about **3.6 points for 100 questions, 2.1 for 300, and 1.1 for 1,000**. So "86.3% versus 85.0%" on 300 questions is well inside one SE. To halve the SE you need four times the questions. Miller's worked example needs about **969 questions** to detect a 3-point difference at 80% power, and he suggests new evals have at least 1,000 ([Miller 2024](https://arxiv.org/html/2411.00640v1)).

### Pairing and discordance set your real power

Because both systems answer the same questions, the right analysis uses the per-question difference. Its SE is usually much smaller than the unpaired one, because scores are correlated ([Miller 2024](https://arxiv.org/html/2411.00640v1)). For binary outcomes, power then depends on the **share of questions where the two systems disagree** (call it psi), not on n alone. McNemar's test uses only those discordant pairs. Worked from Miller's paired formula, on 300 questions the minimum detectable effect is about **3.6 points if 5% of answers change, 5.1 points if 10% change, and 7.2 points if 20% change**. Small prompt tweaks change few answers, which helps. Model swaps change many, which hurts. A concrete worked case: on 300 questions, version B fixes 25 items that A got wrong and breaks 10 that A got right. The gain is +5.0 points. The paired SE is about 1.95 points, giving a 95% interval of roughly **+1.2 to +8.8 points** and an exact McNemar p of about 0.017. Report it that way, "+5.0 points (95% CI +1.2 to +8.8)", because the interval shows both that the gain is probably real and that it might be small. A p-value alone hides the second part. Estimate psi from your own history: count discordant pairs in past A/B runs. Also run the same config twice and count flips. That flip rate is your noise floor.

### Repeats help, but only up to a ceiling

Total variance has two parts: which questions you happened to pick, and the model's randomness on each question. Repeated runs only shrink the second part. In Miller's example, two runs per question remove a third of the total variance, four remove half, and the limit is two thirds ([Miller 2024](https://arxiv.org/html/2411.00640v1)). Two rules follow. First, **average the K runs per question first, then compute the SE across questions**. Never treat 3 × 300 answers as 900 independent samples. Once each question's score is a fraction (for example 2 of 3), McNemar no longer applies directly. Use a paired t-test or permutation test on the per-question means. Second, do not lower the temperature to cut noise. Miller shows it can shift the expected score and even raise variance; resample instead. Repeats also show you something useful: questions that are sometimes right and sometimes wrong ("flaky") hold most of the sampling noise and are good targets for prompt work. For agents that must work every time, use **pass^k** (all k attempts succeed) rather than pass@k (at least one succeeds). On tau-bench, pass^8 fell below 25% for the best mid-2024 models ([Yao et al. 2024](https://arxiv.org/pdf/2406.12045)). A task that passes 90% of the time passes eight times in a row only about 43% of the time.

### Questions from the same document are not independent

If many golden questions come from one document, or are paraphrases, their results move together and the naive SE is too small. In Miller's examples, clustered SEs were **1.9 to 3 times** the naive ones (DROP 1.34 versus 0.44; MGSM 1.62 versus 0.86) ([Miller 2024](https://arxiv.org/html/2411.00640v1)). In a RAG set, cluster by source document. A parsing change that breaks one document can flip 15 questions together. Naive McNemar would call that highly significant when it is really one event. The simple fix is a cluster bootstrap: resample documents with replacement and keep all their questions. For the same total size, many documents with few questions each give more information than few documents with many questions.

### Choose the test and interval to match the score

For a single pass rate, use the **Wilson interval**, not the textbook Wald interval, whose coverage is "persistently poor" for small n or rates near 0% or 100% ([Brown, Cai, DasGupta 2001](https://projecteuclid.org/euclid.ss/1009213286)). On the full 300 questions at 85% the two barely differ. On a 30-question slice where you score 30/30, Wald gives a zero-width interval, while Wilson gives roughly 89-100%. For comparisons, a simulation study of over 500 million p-values on IR metrics found the **paired t-test and permutation test** keep false positives at the stated rate even with 25-100 queries. The bootstrap-shift test gave too many false positives on small sets, and Wilcoxon and sign tests were unreliable ([Urbano, Lima, Hanjalic 2019](https://arxiv.org/abs/1905.11096); [Smucker et al. 2007](https://ciir-publications.cs.umass.edu/getpdf.php?id=744)). So: McNemar (exact form when discordant pairs are few) for single-run pass/fail; paired t or permutation for judge scores, per-query recall, nDCG and averaged repeats; bootstrap for odd statistics like medians or macro-F1, resampling questions or clusters, never individual runs.

### Trying many variants inflates the winner

If you try 20 prompt variants on the same 300 questions and keep the best, the winner looks good even if none is better. Twenty tests at alpha 0.05 give a 64% chance of at least one false win. Under the paired noise level above, the best of 20 useless variants shows about +3.4 points by chance alone (worked from the same SE formula). In IR research, an estimated **40-50% of uncorrected significance claims** are likely false positives ([Otero et al. 2025](https://arxiv.org/html/2501.03930v1)). The fixes are a Holm correction when you compare several variants to a baseline, Tukey HSD for all pairs ([Sakai tutorial](https://es.slideshare.net/TetsuyaSakai/sigir2018tutorial)), and one final check on a held-out test set that played no part in choosing. Every time you look at a holdout and change something because of it, the holdout loses value. Work on the "reusable holdout" shows that the number of safe reuses grows only with roughly the square of the holdout size ([Google Research](https://research.google/blog/the-reusable-holdout-preserving-validity-in-adaptive-data-analysis/)). Forking paths do the same damage without explicit tests: picking the metric, the slice or the one-tailed test after seeing the data. Write the comparison plan down before you run it, and keep the gate rules fixed in code.

### A gate should test "not worse beyond a margin"

A gate that fires on any drop will fire on pure noise about once in 20 runs at alpha 0.05. The rigorous version is a **non-inferiority** check. Block the change only if the lower bound of the paired difference falls below a set margin, for example -2 points. Set that margin from your measured run-to-run spread, not from intuition. A held-out test set of 100 questions can only confirm large changes (paired detectable effect of roughly 6-9 points), so grow and refresh the test set over time.

## Your two judges are classifiers and need a confusion matrix

An LLM judge is a model that predicts a human verdict. Treat the judge prompt as a model under training. The standard recipe from Husain: one domain expert labels outputs pass/fail per criterion, with a written critique. Split the labels into **train 10-20%** (used only as few-shot examples), **dev 40-45%** (where you iterate the prompt) and **test 40-45%** (run once, with the prompt frozen). Have 30-50 passes and 30-50 fails in each of dev and test, about **100-200 labels per criterion** in total. "Below 60 examples, the confidence intervals are often too wide to support a useful conclusion" ([Husain, LLM-judge guide](https://hamel.dev/blog/posts/llm-judge/); [Evals FAQ](https://hamel.dev/blog/posts/evals-faq/)). These numbers are practitioner guidance, not derived results. Fails are usually rare, so over-sample suspected fails (low scores, items the two judges disagree on) to reach enough of them. An informal comparison against analyst scores is, in these terms, one pass over a dev set. The judge's error rates should be reported only from a frozen, unseen test set.

### Report TPR and TNR, not raw agreement

Raw agreement misleads when classes are uneven. If 5% of answers fail, a judge that always says "pass" agrees 95% of the time and catches nothing ([Husain](https://hamel.dev/blog/posts/llm-judge/)). Report the judge as a detector of failures: **TPR** (share of real failures caught), **TNR** (share of good answers correctly passed), precision on "fail", and **Cohen's kappa** as one chance-corrected summary, each with a 95% interval. Kappa matters more than it looks. Two raters who agree 90% of the time, when each says "pass" 85% of the time, have a kappa of only about 0.61 (worked from the kappa formula; [arXiv 2606.00093](https://arxiv.org/html/2606.00093v1)). In one study Llama-3-8B had 80% raw agreement with humans but kappa 0.62, while GPT-4 reached 0.84 against a human-human 0.97 ([Eugene Yan](https://eugeneyan.com/writing/llm-evaluators/)). The ceiling for any judge is the agreement between two analysts on the same items, so label a shared subset twice and measure it. Yan notes that human annotators often reach only 0.2-0.3 kappa and can miss up to half of defects: "The benchmark is human performance, not perfection" ([Yan](https://eugeneyan.com/writing/product-evals/)). Add a fourth number: the judge's consistency with itself across repeated runs. In one study, a strong judge gave the same binary verdict on all three runs for only 61.3% of items ([Rating Roulette](https://arxiv.org/html/2510.27106)). A typical weak pattern is the lenient judge: one evaluator caught consistent summaries over 95% of the time but inconsistent ones only 30-60% of the time ([Yan](https://eugeneyan.com/writing/llm-evaluators/)).

If you keep 1-5 scores, treat the pass threshold as a classifier cut-off. Compute TPR and TNR at each possible threshold (3 or above, 4 or above) on dev labels. Choose by the cost of each error type, and lock the threshold before running on test.

### Correct the pass rate for known judge error

Once TPR and TNR are known, the judge's raw pass rate is biased whenever either is below 1. The **Rogan-Gladen correction** fixes it: true rate = (observed rate + TNR − 1) / (TPR + TNR − 1). It only works if TPR + TNR > 1, meaning the judge is better than chance. The `judgy` library applies it and bootstraps an interval ([judgy](https://github.com/ai-evals-course/judgy)). Lee et al. give a closed-form interval that includes the uncertainty in TPR and TNR themselves. In their simulation the naive judge rate had close to zero coverage, while the corrected interval stayed near 95%. They also show that with a very large unlabelled set, the interval width depends only on how many calibration labels you have. For a moderately good judge, about 200 labels give an interval narrower than 10 points ([Lee et al. 2025](https://arxiv.org/html/2511.21140v3)). So a sound report reads "judge pass rate 82%, corrected 76% [95% CI 70-82%]", not "82%". **Prediction-powered inference** (PPI) is the general version. It combines many judge labels with a small random human-labelled set, adds the average human-minus-judge gap as a correction, and gives valid intervals for any mean, including graded scores ([Angelopoulos et al. 2023](https://arxiv.org/abs/2301.09633)). In IR evaluation, PPI reached 95% coverage with fewer than 20-40 labelled queries ([Oosterhuis et al. 2024](https://arxiv.org/html/2407.02464v1)). The trade-off: Rogan-Gladen accepts an enriched calibration set (TPR and TNR do not depend on the share of fails), while PPI needs a random sample.

### Known biases have known fixes

The documented judge biases are position (in pairwise tests), verbosity, self-preference, leniency, and being misled by the answer under review. The strongest single lever for correctness is **reference-guided grading**. On math questions GPT-4 accepted wrong answers 70% of the time with a default prompt, 30% when told to solve the problem first, and 15% when given a reference answer ([Zheng et al. 2023](https://arxiv.org/pdf/2306.05685)). For grounding, the same logic says: have the judge list each claim and its supporting passage before it gives a verdict. Self-preference is real. Models rate their own outputs higher, and the effect grows with how well they recognise their own text ([Panickssery et al. 2024](https://arxiv.org/abs/2404.13076v1)). Judges from different families help. A panel of three small judges from different families beat a single GPT-4 judge on kappa against humans (for example 0.763 versus 0.627 on NQ), with less own-family bias and at 7-8 times lower cost ([Verga et al. 2024](https://arxiv.org/html/2404.18796v2)). Small prompt edits move agreement a lot: GPT-4's kappa on NQ ranged from 0.518 to 0.725 with prompt changes alone ([Verga et al.](https://arxiv.org/html/2404.18796v2)). Anthropic adds: one isolated judge per dimension, and an "Unknown" option so the judge does not make up a grade ([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).

### Two judges need an explicit combining rule

With two judges, majority vote is not defined. You choose among "fail if either fails" (catches more, more false alarms), "fail only if both fail" (the reverse), or "agree means automatic, disagree goes to a human". Each rule is its own classifier with its own TPR and TNR on the test set. Pick by error cost, then apply the correction with that rule's rates. Report each judge separately too, so a drop in one after a vendor update is visible. Low agreement between the two judges on a criterion often points to an unclear rubric rather than a bad judge. No study measures two-judge panels directly; the evidence is from three-judge panels.

### Any change resets the judge's error rates

A new judge model, prompt, scale, or a new generator that makes new kinds of mistakes all invalidate the measured TPR and TNR ([Husain](https://hamel.dev/blog/posts/llm-judge/)). A workable protocol: pin judge model and prompt versions; re-run the frozen test set in CI on any judge change and block it if TPR or TNR falls outside the previous interval; have the analyst label 30-50 fresh production items each month; move fresh disagreements into dev and rotate in a new test set once dev has absorbed the old one; and watch inter-judge agreement in production as an alarm that needs no labels.

## Prompt tuning is controlled experimentation, not editing

The disciplined loop is: read traces, count failure categories, pick the top one, write a hypothesis, make **one change**, run a paired comparison on dev, keep it only if the target category improves without regressions elsewhere, and touch the test split only at the end ([Evals FAQ](https://hamel.dev/blog/posts/evals-faq/)). Each experiment record should carry the prompt version, model ID, sampling settings, dataset version, hypothesis and **per-item scores**. Paired tests need per-item scores; a mean alone is not enough. Prompts that have grown many rules benefit from ablation: remove one section at a time and re-run dev. Sections whose removal changes nothing are bloat. This matters because instruction-following falls as rule count rises. Even the best frontier models reach only about 68% accuracy with 500 simultaneous instructions, and they favour earlier ones ([IFScale](https://arxiv.org/abs/2507.11538)). A useful rule: every prompt rule names the failure it fixes and the eval items that show the fix.

### Spurious changes move scores, so one run is not a measurement

Formatting alone (separators, casing, spacing) changed few-shot accuracy by up to **76 points** on LLaMA-2-13B. The sensitivity persisted in larger and instruction-tuned models, and the best format did not transfer between models ([Sclar et al. 2023](https://arxiv.org/abs/2310.11324)). The order of few-shot examples can swing a model from near state of the art to near random ([Lu et al. 2022](https://arxiv.org/abs/2104.08786)). Frontier models are more robust, and LLM-judge prompts are also sensitive ([ProSA](https://arxiv.org/abs/2410.12405)). Placement matters on Claude: long documents first and the question last "can improve response quality by up to 30 percent in tests" ([Anthropic prompting guide](https://platform.claude.com/docs/build-with-claude/prompt-engineering/claude-prompting-best-practices)). The consequence for a 300-question set is direct. A tweak worth 2-3 points sits below what you can detect. Accept such a change on qualitative grounds (it fixes a named failure, shown on specific items) plus a non-inferiority check, rather than claiming a measured gain.

### Automatic optimisers need a trustworthy metric first

DSPy's optimisers (BootstrapFewShot, MIPROv2, GEPA), OPRO and TextGrad all need a programmatic metric and a training set: from about 10 examples for few-shot bootstrapping to **200+ for long MIPROv2 runs "to limit overfitting"**. A typical DSPy run costs about $2 ([DSPy docs](https://github.com/stanfordnlp/dspy/blob/main/docs/docs/learn/optimization/optimizers.md)). Reported gains are large on weak baselines: a ReAct agent went from 24% to 51% with MIPROv2, and GEPA reports over 10% above MIPROv2 ([DSPy docs](https://github.com/stanfordnlp/dspy/blob/main/docs/docs/learn/optimization/optimizers.md); [Agrawal et al. 2025](https://arxiv.org/abs/2507.19457)). On a carefully written prompt for a frontier model, expect smaller gains. An optimiser maximises the metric, so a judge that likes long answers will be exploited. Use optimisers when the metric is validated, you have 50-200+ labels, or you are migrating to a cheaper model. Verify on the held-out test split, add a length or cost penalty, and review the final prompt diff by hand. Inspect disagreements manually before tuning automatically, or you will miss problems that are not in the prompt, such as missing context or bad labels ([Evals FAQ](https://hamel.dev/blog/posts/evals-faq/)).

### Score abstention, or tuning drifts toward guessing

Accuracy-only scoring rewards guessing. On SimpleQA, one model abstained 52% of the time with 26% errors, while another abstained 1% with **75% errors** and only slightly higher accuracy ([OpenAI 2025](https://openai.com/index/why-language-models-hallucinate/)). Score each golden item as correct, wrong or abstained, with wrong costing more than abstained. Report coverage (share answered) alongside accuracy on answered items. Verbalised confidence ("I am 90% sure") is overconfident. Agreement across several sampled answers is the better-supported signal ([Xiong et al. 2024](https://arxiv.org/abs/2306.13063)). The golden set needs unanswerable questions, or abstention is never rewarded.

### Model upgrades are migrations

Prompts do not port cleanly between models. Anthropic says to treat a model-specific technique as "measured on that model and re-check it against your own evals". Newer Claude models follow instructions more literally, so emphatic rules written for older models ("CRITICAL: You MUST…") now cause over-triggering ([Anthropic prompting guide](https://platform.claude.com/docs/build-with-claude/prompt-engineering/claude-prompting-best-practices)). A migration eval is: same golden set, same pinned judge, paired comparison per item, a manual read of every item that flipped from pass to fail, and fresh error analysis to find new failure categories. Removing compensating rules is often the fix.

## Retrieval tuning needs labels that survive re-chunking

Recall@k and MRR are per-query averages, so everything above applies: SE, paired tests, and clustering by document. Recall@k with one relevant chunk per query is a 0/1 pass rate, so use Wilson intervals and McNemar. With several relevant chunks it is graded, so use paired t or permutation. MRR is dominated by the jump from rank 1 to rank 2 (1.0 to 0.5), so a reranker that swaps the top two on a few queries can move it a lot. Check MRR changes with a paired test, not by eye. On 300 questions, a 90% recall estimate has a 95% interval of about ±3.4 points.

### Label spans, not chunk IDs, and expect incomplete judgments

If gold labels are chunk IDs, every chunking experiment quietly invalidates them. Chroma's chunking study defines relevance by **token spans** of a relevant excerpt and scores any retrieved chunk against those tokens ([Chroma](https://www.trychroma.com/research/evaluating-chunking)). Store each gold answer as (document, version, span) and decide at eval time which chunks overlap it. Labels are also incomplete. A new system may find valid passages nobody labelled, and it gets scored as worse. On BEIR's TREC-COVID, up to **32% of dense retrievers' top-10 results** had never been judged. After the missing pairs were judged, ANCE's nDCG@10 rose from 0.654 to 0.735 and it moved clearly above BM25 ([BEIR](https://arxiv.org/html/2104.08663v4)). The fix is pooling. Before you conclude a new retriever is worse, judge the union of all variants' top-k on a sample of questions. Synthetic queries are reliable for ranking systems against each other but biased for absolute numbers. They are longer than real queries and favour LLM-based systems ([Rahmani et al. 2025](https://arxiv.org/html/2506.10301v2)). They also tend to paraphrase the chunk they came from, which flatters dense retrieval. Report synthetic and real-user slices separately.

### Recall is a necessary gate, not proof of answer quality

Conventional relevance labels correlated only weakly with downstream RAG answer quality. eRAG, which labels each document by whether the generator answers correctly from that document alone, correlated much better (Kendall's tau gains of 0.168-0.494) ([Salemi & Zamani 2024](https://arxiv.org/abs/2404.13781v1)). Answer accuracy also does not follow recall upward. Recall keeps rising with more context, but many models' accuracy peaked between 4k and 32k tokens of retrieved context and then fell ([Databricks](https://www.databricks.com/blog/long-context-rag-performance-llms)). So a recall@5 gate is reasonable if four conditions hold. Set k to the number of chunks the generator really sees after reranking. For multi-hop questions, count recall as "all required spans found". Gate per segment (question type, document family), not only on the average; Jason Liu notes that 70% overall recall can hide 5% on multi-hop or date-filter queries ([Liu 2025](https://jxnl.co/writing/2025/01/24/systematically-improving-rag-applications/)). And pair the gate with a "sufficient context" check on a sample. An autorater can judge whether the retrieved context is enough to answer with 93% accuracy ([Joren et al. 2024](https://arxiv.org/abs/2411.06037v3)).

### Separate retrieval faults from generation faults

Run the generator three ways: with retrieved context, with gold (oracle) context, and with no context. If oracle accuracy is low, the fault is the prompt, the generator or the label. If oracle is high and real retrieval is low, the fault is retrieval. No-context accuracy shows how much the model answers from memory, which hides retrieval failures and is risky for regulated content. Add the sufficiency check and you get a 2×2 table. Sufficient and wrong is a generation fault. Insufficient and wrong is a retrieval fault. Insufficient and right is luck or memory. Models still answered correctly 35-62% of the time with insufficient context, so end-to-end accuracy can mask retrieval problems ([Joren et al. 2024](https://arxiv.org/abs/2411.06037v3)). Also split **candidate recall** (recall@100-150 before the reranker) from **final recall** (after it). If candidate recall is low, only first-stage changes help: hybrid search, chunking, embeddings or query rewriting. If candidate recall is high and final recall is low, tune the reranker or k.

### Categorise misses, then pick the knob

For each miss, log the top 20 results and assign one cause: vocabulary mismatch, chunk boundary, wrong document or version, multi-hop, broad or summary question, not in the corpus or lost in parsing, or a label error. Liu separates "inventory" problems (the data is not indexed) from "capability" problems (it is there but search cannot surface it) ([Liu 2025](https://jxnl.co/writing/2025/01/24/systematically-improving-rag-applications/)). Each cause has a typical fix. The best-evidenced levers are hybrid lexical plus dense retrieval, a cross-encoder reranker over a wide candidate set, and contextual chunk headers. In Anthropic's tests, contextual embeddings plus contextual BM25 plus reranking cut the top-20 failure rate by **67%** (5.7% to 1.9%) ([Anthropic](https://www.anthropic.com/news/contextual-retrieval)). BM25 plus a cross-encoder beat BM25 on 16 of 18 BEIR datasets, and dense models often lost to BM25 out of domain ([BEIR](https://arxiv.org/html/2104.08663v4)). That makes hybrid search worth testing wherever users type exact codes, section numbers or names. Chunking strategy moved recall by up to about 9 points, heavy overlap hurt efficiency, and the best chunker changed with the embedding model ([Chroma](https://www.trychroma.com/research/evaluating-chunking)). For fusion, a tuned weighted combination of normalised scores beat reciprocal rank fusion, and RRF turned out to be sensitive to its parameter ([Bruch et al. 2022](https://arxiv.org/abs/2210.11934)). Leaderboards are priors, not decisions: no embedding model dominates MTEB across tasks ([MTEB](https://arxiv.org/abs/2210.07316)). Order experiments by cost. Reranking, fusion weights, k and query rewriting need no re-index. Chunking, contextual text and embedding model changes need one, so cache embeddings per configuration. Change one knob at a time against a fixed baseline. Use a small grid only where knobs are known to interact, such as chunk size with embedding model.

## Graph search earns its cost only on specific question types

"GraphRAG" covers designs that differ a lot. There are LLM-built entity graphs with community summaries for whole-corpus themes (Microsoft GraphRAG). There are cheap query-time concept graphs (LazyGraphRAG) and graph-as-index multi-hop retrievers (HippoRAG 2). And there are true knowledge graphs queried with Cypher or SQL over data you already model ([Edge et al. 2024](https://arxiv.org/abs/2404.16130); [Microsoft Research](https://www.microsoft.com/en-us/research/blog/lazygraphrag-setting-a-new-standard-for-quality-and-cost/); [Gutiérrez et al. 2025](https://arxiv.org/abs/2502.14802)). The first three compete with vector search over documents. The last competes with text-to-SQL. Most benchmark arguments are about the first group.

### Independent studies: graphs help multi-hop and themes, hurt simple facts

The original GraphRAG paper reported 72-83% comprehensiveness win rates over vector RAG. Those came from LLM pairwise judging on generated "global" questions, with no ground-truth accuracy ([Edge et al. 2024](https://arxiv.org/html/2404.16130)). An independent re-test showed that protocol is badly biased. LightRAG against an **identical copy of itself scored 90% to 10%**. Swapping answer order moved win rates by over 30 points, and a 25-token length gap moved them by over 50. Under a debiased protocol, LightRAG's win rate over plain RAG fell from 66.7% to 39%, with ties above 20% ([arXiv 2506.06331](https://arxiv.org/html/2506.06331v1)). Han et al.'s unified comparison found plain RAG at or above graph methods on single-hop questions (NQ F1 64.78 for RAG against 54.48 for global GraphRAG). Graph methods won on comparison and temporal questions (temporal 30.70 against 53.34). Global search collapsed on "insufficient information" questions (19.27% against RAG's 96.01%). Only about **65% of answer entities** made it into the LLM-built graph at all ([Han et al. 2025](https://arxiv.org/html/2502.11371)). Most striking, GraphRAG retrieved about 9,770 tokens per query against RAG's 3,631. When RAG got the same budget, the gap vanished (71.01 against 71.17). GraphRAG-Bench (ICLR 2026) agrees: RAG with a reranker led on fact retrieval, graphs led on complex reasoning and summarisation, and the same method flipped from winner to loser between a novel corpus and a medical corpus ([Xiang et al. 2026](https://arxiv.org/html/2506.05690v3)). The HippoRAG 2 authors themselves state that earlier structure-augmented methods underperform strong embedding RAG ([Gutiérrez et al. 2025](https://arxiv.org/html/2502.14802v2)). Vendor claims of doubled accuracy exist but contradict themselves and should carry little weight ([Neo4j](https://neo4j.com/blog/agentic-ai/vector-rag-vs-graphrag/)). Two findings point toward combining rather than replacing. On MultiHop-RAG, 13.6% of queries were right only with GraphRAG and 11.6% only with RAG, and concatenating both contexts beat either one by 6.4% ([Han et al.](https://arxiv.org/html/2502.11371)).

### The costs are an order of magnitude or more

On one corpus, Microsoft GraphRAG used **115.5M input tokens and 277 minutes** to index, and took 10.7 s per query. Dense retrieval took 12.1 minutes, no LLM tokens, and 0.3 s per query. HippoRAG 2 sat between them at 9.2M tokens and 1.2 s ([HippoRAG 2, Table 12](https://arxiv.org/html/2502.14802v2)). Prompt tokens per query ranged from 879 for vanilla RAG to 331,375 for GraphRAG global ([GraphRAG-Bench](https://arxiv.org/html/2506.05690v3)). New documents can reshape communities so that "much of an index needs to be re-computed" ([Microsoft, GraphRAG 1.0](https://www.microsoft.com/en-us/research/blog/moving-to-graphrag-1-0-streamlining-ergonomics-for-developers-and-users/)). LazyGraphRAG is the cheap exception. Its indexing costs match vector RAG, though that claim comes from the method's authors.

### A decision rule and a fair test protocol

Decide from failure analysis on your own questions. The evidence supports this mapping. Single facts in one passage go to hybrid search plus a reranker; a graph adds noise. Scope questions ("in the 2025 edition") go to metadata filters. Answers that depend on a document's structure (a definition elsewhere, a table under a heading) go to structure-aware chunking and section or parent retrieval. That is a cheap, exact document-hierarchy graph, not an LLM-extracted one. "List all" and count questions go to SQL or a typed index, because top-k retrieval cannot guarantee completeness. Multi-hop questions across documents should first try entity linking in the style of HippoRAG 2, or agentic iterative retrieval. Relationship and path questions over known entities go to a modelled knowledge graph fed from source systems; some of these are unreachable by vector search at all ([arXiv 2606.06003](https://arxiv.org/abs/2606.06003)). Whole-corpus themes go to LazyGraphRAG, GraphRAG global, or map-reduce over summaries. Where the system must reliably say "not found", avoid global community search. Whether an agent with a few retrieval tools captures most of the multi-hop gain without a graph is plausible but untested head to head.

A fair comparison has eight steps. First, label each golden question by type and aim for 20-30+ per type you care about (a rule of thumb). Second, build a strong baseline first (hybrid, reranker, structure-aware chunks, filters), because many graph wins vanish against a tuned baseline. Third, run the oracle checks: gold evidence to the generator, gold evidence in each system's top-k, and answer-entity coverage in the graph. Fourth, match token budgets. Fifth, score with deterministic checks or required facts ("assertions", as BenchmarkQED does), not pairwise preference alone ([BenchmarkQED](https://www.microsoft.com/en-us/research/?p=1140429)). Sixth, if you use pairwise judges, swap order, allow ties, repeat, and run the self-versus-self sanity check, which should land near 50/50. Seventh, use paired tests per type with intervals: McNemar for right/wrong, paired t or permutation for scores (prefer these over Wilcoxon, per the simulation evidence above). Eighth, record cost, p50/p95 latency and re-index cost. Count only-A-right against only-B-right questions. Adopt graph retrieval only for the types where it wins by more than the noise.

## What you likely do now, and the rigorous version

| Area | What you likely do now | The rigorous version |
|---|---|---|
| Choosing what to evaluate | Golden set built from question categories (happy, negative, vague, out of scope, attack, multi-turn) | Categories come from counted failure modes found in trace reading; first-failure coding; saturation; new modes added, saturated evals retired |
| Score format | Judges score 1-5 on three criteria, pass at a threshold | Binary verdict per criterion with a critique, or a threshold chosen on dev by TPR/TNR and locked; binary sub-checks for graded progress |

| Reported pass rate | Raw judge pass rate | Rogan-Gladen corrected rate with an interval (or PPI for graded means) |
| Two judges | Two families, scores compared | Explicit combining rule validated as its own classifier; per-judge rates tracked; disagreement routed to humans and into dev |
| Judge maintenance | Judge prompt edited when needed | Pinned versions; CI re-runs test set on any judge change; monthly fresh labels; test set rotated once tuned on |
| Uncertainty | Point estimates per run | SE and n beside every number; Wilson for rates and slices; paired difference with 95% CI |
| Repeats | Three runs per question | Average per question first, SE across questions; flaky items flagged; pass^k where reliability matters; temperature left at production value |
| Comparisons | McNemar between design choices | McNemar for single-run binary; paired t or permutation for averaged or graded scores; clustered by source document; power planned from your own discordance rate |
| Many variants | Try variants, keep the best | Plan written first; Holm correction; winner confirmed once on held-out test |
| Held-out split | One split kept aside | Dev for iteration, test touched rarely, refreshed and grown; dev-test gap tracked as an overfitting signal |

| Retrieval metrics | Recall@k and MRR, before and after reranker | Candidate recall versus final recall; k equal to real context size; "all spans found" for multi-hop; sufficiency check; oracle and no-context runs |
| Prompt changes | Edit and re-run | One hypothesis per change; per-item scores logged; ablation of old rules; abstention scored; migration protocol on model change |
| Graph versus vector | Architecture debate | Per-type labelled set, tuned hybrid baseline, matched tokens, debiased judges, complementarity count, cost and update burden |

## Questions for a grilling session

1. Your 300-question set shows a new prompt at 87% against 85% for the old one. Walk through exactly what you would compute before calling it an improvement, and what discordance rate you would need for that gain to be detectable.
2. Why does McNemar's power depend on the discordant pairs and not on the total number of questions? What does that imply for model swaps versus small prompt tweaks?
3. You run each question three times. Show how you compute the SE and the paired test correctly, and explain why pooling 900 answers is wrong. Why does a fourth or fifth run help less and less?
4. Fifteen golden questions come from one document whose parsing changed. How does that affect the significance of a recall change, and how would a cluster bootstrap fix it?
5. Your judge agrees with the analyst on 90% of items. Why might that still be a weak judge? Compute kappa if both say "pass" 85% of the time, and say which two other numbers you would report.
6. Design the labelled set for validating the grounding judge: who labels, how many items, how you get enough fails, the split, and which numbers come from which split.
7. The judge's raw pass rate is 82%, with TPR 0.90 and TNR 0.70 on the test set. What is the corrected rate, when does the correction break down, and what does it assume about production data?
8. With two judges, which combining rule would you choose for a regulated domain, and how do you measure the combined rule's error rates?
9. You tried 12 prompt variants and the best gained 3 points on dev. What is your next step, and why is "ship it" the wrong answer?
10. Rewrite the regression gate "judge pass ≥ 85%" as a non-inferiority test. Where does the margin come from, and how often would the current gate fire on noise alone?
11. A new embedding model scores lower recall than the old one. Name two reasons that could be a measurement artefact rather than a worse model, and how you would rule each out.
12. Describe the oracle, no-context and sufficiency tests. Fill in the 2×2 table and say what action each cell leads to.
13. Recall@5 is 93% but users still get wrong answers. List at least four explanations the recall number cannot see.
14. A vendor shows GraphRAG winning 75% of pairwise comparisons against your RAG. What three checks would you run before believing it, and what result from the self-versus-self test would make you throw the number out?
15. For each question type in a golden set (single fact, version-scoped, list-all, multi-hop, relationship, whole-corpus theme, unanswerable), say whether you would use vector, hybrid, metadata filters, SQL, a document-structure tool or a graph, and why.

## Conclusion

The shift is from "running evals" to "knowing what an eval can and cannot tell you". Every number in the pipeline is an estimate with an error: the golden-set score, the judge's verdict, the recall figure, even the gold label. The rigorous habit is to attach that error to the number before you act on it. A 300-question set and three runs per question are a good base. The higher-value investments are not more questions but better ones (counted failure modes, span-level labels, typed questions), a judge with a measured confusion matrix and a corrected pass rate, and gates that test for real harm rather than any wobble.

The graph-versus-vector question looks different through this lens. It is mostly a measurement question, not an architecture question. Once token budgets are matched and judges are debiased, the published evidence says graphs win only on some question types: multi-hop, comparison, temporal and whole-corpus themes. They lose on simple facts and on saying "not found", and they cost one to two orders of magnitude more to build and keep fresh. The sensible default is a tuned hybrid baseline plus structure-aware tools, with graph retrieval added as an extra lane only for the question types where your own paired, per-type tests show a gain larger than the noise.
