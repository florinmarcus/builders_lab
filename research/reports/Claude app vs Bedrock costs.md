# Build the small Bedrock app, demo in Claude

For the pilot, our own small web app calling Claude on Amazon Bedrock is both cheaper and easier to get approved than using the Claude app as the client. With two users and about 500 questions a month, the Bedrock route costs about **$25 a month on Haiku 5.5 or $38 a month on Sonnet 5.5**, almost all of it the server. The Claude app route costs about **$64–74 a month** before an identity provider, because we still run the same server and ingestion, and add two Claude seats on top. Cost is the smaller point. A council treats the contractor as its data processor and needs to approve every sub-processor. Bedrock in London keeps processing in the UK/EU under AWS's automatic UK GDPR terms, and Anthropic never sees the data. The Claude app sends every tool result through Anthropic's cloud, with processing in the US. On Pro or Max there is no processor agreement at all, so those plans cannot hold tenant data. The Claude app is still useful: it is the fastest way to demo the backend to Builder 1 with mock data, and an MCP server we build now keeps that door open. All prices are in USD, checked 18 Nov 2026, and the usage figures are our own estimates, not quotes.

## The server costs more than the model, in both routes

The two routes share most of their cost. In both, our backend reads the council emails, extracts the PDFs, links documents to properties, embeds them and stores them in Postgres with pgvector. That backend needs one small server. A **Lightsail 4 GB bundle costs a flat $24 a month** in London or Frankfurt, with SSD, a public IPv4 address and 4 TB of transfer included ([AWS Lightsail pricing](https://aws.amazon.com/lightsail/pricing/)). The EC2 alternative, a t4g.medium in London at $0.0376 an hour ([AWS EC2 price list, London](https://b0.p.awsstatic.com/pricing/2.0/meteredUnitMaps/ec2/USD/current/ec2-ondemand-without-sec-sel/EU%20(London)/Linux/index.json)), comes to about $34 once a 30 GB gp3 disk and the $0.005-an-hour IPv4 charge are added ([AWS VPC pricing](https://aws.amazon.com/vpc/pricing/)). The one-off ingestion is also shared. On our assumption of 50 flats, 15 documents each and 10 pages per document, extracting 7,500 pages with **Haiku 5.5 costs about $1.30–3.00**, and Titan Text Embeddings V2 adds about $0.75 at London's $0.0001 per 1,000 tokens ([AWS Bedrock price list, London](https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AmazonBedrock/current/eu-west-2/index.json)).

The routes differ only in who pays for the questions. In our own app, we pay Bedrock per token. Bedrock's EU geo price is the Anthropic list price plus 10%: **Haiku 5.5 at $0.11 in / $0.55 out per million tokens, Sonnet 5.5 at $2.20 / $11.00**, the same in London and Frankfurt ([AWS Bedrock model price list, London](https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AmazonBedrockFoundationModels/current/eu-west-2/index.json); [Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)). At 500 questions a month, each with 10,000 tokens in and 600 out, that is **$0.72 a month on Haiku 5.5 and $14.30 on Sonnet 5.5**. In the Claude app, the questions run on each user's Claude subscription. Pro is $20 a month (or $17 billed yearly), and Team Standard is $25 a seat monthly (or $20 yearly), "for teams of 2 to 150" ([Claude pricing](https://claude.com/pricing)).

| Monthly cost, 2 users, ~500 questions (USD, 18 Nov 2026) | Own web app on Bedrock | Claude app + our MCP server |
|---|---|---|
| Server (Lightsail 4 GB) | $24.00 | $24.00 |
| Questions | $0.72 (Haiku 5.5) to $14.30 (Sonnet 5.5), EU geo | $0 to us; on the users' seats |
| Claude seats | none | $40–50 (2 Team seats) |
| OAuth identity provider | not needed (simple login) | not priced |
| **Total per month** | **≈ $25–38** | **≈ $64–74 + identity provider** |
| One-off ingestion (Haiku 5.5 + Titan V2) | ≈ $2–4 | ≈ $2–4 (same backend) |

The Bedrock route is cheaper by roughly $25–50 a month, and it scales with use instead of seats. A third user adds a few cents on Haiku, not another $25 seat. Two caveats cut both ways. Haiku 5.5 and Sonnet 5.5 think adaptively by default, and thinking tokens are billed as output ([Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)), so Sonnet could cost more than $14.30. On the other side, the Claude app's seat price buys a finished chat interface, chat history and mobile apps, which the Bedrock route must build. New AWS accounts get $100–200 in credits ([AWS Free Tier](https://aws.amazon.com/free/)), but no source confirms these credits pay for Claude on Bedrock, which AWS bills as a Marketplace item.

## The Claude app saves the chat screen but adds an OAuth server

The Claude app looks like less work: the backend we must build anyway becomes a remote MCP server, and Claude supplies the chat, the history and the phone app. Any plan can add a custom connector by pasting the server URL, with **no review by Anthropic** ([Build an MCP server for Claude](https://claude.com/docs/connectors/building.md)). A connector added on the web also works on desktop and mobile ([Claude Help: custom connectors](https://support.claude.com/en/articles/11175166-getting-started-with-custom-connectors-using-remote-mcp)). Since January 2026 a server can also draw interactive views inside the chat, such as a property table with buttons, on web, desktop and mobile ([Claude blog, 26 Jan 2026](https://claude.com/blog/interactive-tools-in-claude)). The Python MCP SDK makes the server itself a small job.

The hidden cost is authentication. Claude calls the server from Anthropic's cloud (`160.79.104.0/21`), so the server must sit on the public internet on port 443. An authless server would let anyone with the URL read council data. The safe path is per-user OAuth: an authorization server with PKCE S256, dynamic client registration or client ID metadata documents, discovery metadata, a `401` with the right `WWW-Authenticate` header, and token endpoints that answer within 10 seconds ([Claude docs: authentication for connectors](https://claude.com/docs/connectors/building/authentication.md)). A simpler fixed API-key header exists, but it is a beta for "a limited set of organizations" and shares one key across the whole team ([same](https://claude.com/docs/connectors/building/authentication.md)). For two users, a full OAuth server is more work than the username-and-password login that ADR 0003 already plans behind HTTPS.

The tool results also have limits. On claude.ai a tool result can be about **150,000 characters** and a call can run **240 seconds**; sampling and resource subscriptions are not supported ([Build an MCP server for Claude](https://claude.com/docs/connectors/building.md)). That suits a search tool that returns the top few chunks, but not whole PDFs. No official page says whether a photo or PDF the builder uploads in chat reaches our tools, or how source links render. Our own app controls all of this: it can show the original council PDF next to the answer and keep each answer tied to its property.

The Bedrock route's extra work is real but small and familiar. We build a mobile-friendly chat page, store chat history in the Postgres we already run, and call Bedrock from the backend through an IAM role. We give up Claude's polished mobile apps and their future features. We gain full control of the prompt, the model choice per task, the Romanian wording, and what each answer shows.

## Council approval favours Bedrock in London by a wide margin

The deciding factor is the council's data rules. Councils treat repair contractors as data processors under UK GDPR, and their contract schedules forbid sub-processors without written authorisation ([North Northamptonshire schedule](https://www.contractsfinder.service.gov.uk/Notice/Attachment/ecb1afb5-a790-4c3c-8fbf-e49993c5ce88)). The emails hold tenant contact details, access notes and vulnerability indicators ([RBKC DPIA](https://www.rbkc.gov.uk/Committees/documents/s36760/ED5014342R3%20DPIA.pdf)). So whatever model service we use becomes a sub-processor the council must accept.

Bedrock gives the simplest chain. AWS's UK GDPR Addendum, with the ICO's IDTA, "applies automatically for all customers who require a data processing agreement" ([AWS GDPR Center](https://aws.amazon.com/compliance/gdpr-center/)). Bedrock does not use prompts or outputs to train models and does not share them with model providers ([Bedrock FAQs](https://aws.amazon.com/bedrock/faqs/)). Models run in AWS-owned accounts where providers "don't have access to Amazon Bedrock logs or to customer prompts and completions" ([Bedrock data protection](https://docs.aws.amazon.com/bedrock/latest/userguide/data-protection.html)). In practice, the council approves one well-known sub-processor, AWS, and Anthropic stays out of the data path.

The location story is good but not perfect. London offers Claude through the global endpoint and the EU geo profile, not in-region only. In Europe, in-region-only routing is offered in Stockholm and Ireland ([Claude in Amazon Bedrock](https://platform.claude.com/docs/en/build-with-claude/claude-in-amazon-bedrock)). An AWS blog says EU-profile requests from London route only between EU Regions and London ([AWS ML blog](https://aws.amazon.com/blogs/machine-learning/unlocking-ai-flexibility-in-europe-a-guide-to-cross-region-inference-for-eu-data-processing-and-model-access/)). So inference stays in the UK/EU but may leave the UK. One secondary page claims London has in-region inference for some older Claude models, but the AWS source returned 404, so we treat it as unverified. Data at rest stays in the AWS Region we use ([Bedrock FAQs](https://aws.amazon.com/bedrock/faqs/)), so a London server and London Bedrock keep stored data in the UK.

The Claude app route splits by plan. **Pro and Max fall under the Consumer Terms**: no DPA, and the rule that you "may not make your Account available to anyone else" ([Consumer Terms](https://www.anthropic.com/legal/consumer-terms)). Training is a user setting; with it on, chats are kept five years, and even opted-out chats are trained on if flagged for safety review or rated with thumbs up or down ([Updates to Consumer Terms](https://www.anthropic.com/news/updates-to-our-consumer-terms); [Consumer Terms](https://www.anthropic.com/legal/consumer-terms)). The ICO says a provider that uses customer data for its own training is unlikely to be a mere processor ([ICO generative AI fifth call for evidence](https://ico.org.uk/about-the-ico/what-we-do/our-work-on-artificial-intelligence/generative-ai-fifth-call-for-evidence)). Pro is therefore fine for mock-data demos and unsafe for tenant data. **Team falls under the Commercial Terms**, which include Anthropic's DPA automatically, with no training by default and the ICO's UK transfer addendum ([Anthropic DPA](https://www.anthropic.com/legal/data-processing-addendum); [Commercial Terms](https://www.anthropic.com/legal/commercial-terms)). But Anthropic's API offers only "global" or "us" inference, and "us" is the only workspace geo ([Data residency docs](https://platform.claude.com/docs/en/manage-claude/data-residency)). A request for EU residency in claude.ai suggests the app has none ([GitHub issue 40526](https://github.com/anthropics/claude-code/issues/40526)). The council would have to approve Anthropic, its whole sub-processor list, and US processing. Anthropic may add sub-processors with a 15-day objection window, which the contractor must pass on to the council. Tool results also become part of the chat, so the plan's retention rules apply to the council data our server returns.

## Each route carries a different kind of risk

The Claude app's main risk is dependence on a product we do not control. Developers report custom connectors that fail at sign-in on web and mobile, including on a Team plan, and one that "worked reliably via claude.ai web and iOS until approximately April 15, 2026" ([GitHub #410](https://github.com/anthropics/claude-ai-mcp/issues/410); [GitHub #280](https://github.com/anthropics/claude-ai-mcp/issues/280); [GitHub #215](https://github.com/anthropics/claude-ai-mcp/issues/215)). We read these issues only as search snippets and did not check whether they are fixed. Usage limits are a second risk: paid plans have a 5-hour and a weekly limit, Anthropic warns that "tools and connectors are token-intensive", and it publishes no message counts ([Claude Help: usage limits](https://support.claude.com/en/articles/11647753-understanding-usage-and-length-limits)). A builder who hits the limit on a busy morning cannot get an asbestos answer, and we cannot fix it. On Team, only Owners add connectors, so the contractor's account owner, not us, controls access.

The Bedrock route's risks are ours to manage: we run the server, patch it, back it up and build the chat screen. Two Bedrock gaps matter. The Frankfurt and London price lists have **no batch rows for the 5.5 models**, so the 50% batch discount is not available for ingestion ([AWS Bedrock model price list, Frankfurt](https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AmazonBedrockFoundationModels/current/eu-central-1/index.json)); on Haiku that costs about a dollar. And **rerank is priced only in Frankfurt**, Amazon Rerank at $1 and Cohere Rerank 3.5 at $2 per 1,000 search units ([AWS Bedrock price list, Frankfurt](https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AmazonBedrock/current/eu-central-1/index.json)), so a London build either skips rerank or sends queries to Frankfurt. ADR 0003 already expected this. The Claude 5.5 models on Bedrock also need model access checked in the console ([Claude in Amazon Bedrock](https://platform.claude.com/docs/en/build-with-claude/claude-in-amazon-bedrock)).

A middle path is worth naming. The same backend can expose its tools both to our web app and as an MCP server. ChatGPT also accepts custom MCP servers and its Apps SDK is compatible with MCP Apps ([OpenAI developers](https://developers.openai.com/apps-sdk); [Get started with MCP Apps](https://claude.com/docs/connectors/building/mcp-apps/getting-started.md)), so an MCP layer is not a lock-in to one chat app. Adding it later costs little if the tools are cleanly separated now.

## Conclusion

The question looked like a build-versus-buy choice, but the Claude app does not remove the build. It replaces only the chat screen, and in exchange adds an OAuth server, a per-seat bill, and a second company in the council's data chain. For a pilot whose first customer is bound by a council's sub-processor rules, the cheaper route is also the one with the shorter approval conversation: our own small web app, a London server, Claude on Bedrock through the EU profile, Haiku 5.5 by default and Sonnet 5.5 where answer quality needs it.

The Claude app still has a job. With mock data only, Florin can add a test MCP server to a Claude account (even Free allows one custom connector) and show Builder 1 the backend in a real chat within days, before the web app exists. That demo tests the tools and the Romanian answers, which are the parts that carry over to either client. The open items that could change this verdict are three: whether the council would accept Anthropic and US processing at all, whether AWS credits cover Claude on Bedrock, and how many tokens real council PDFs and thinking actually use. A test run on 5–10 mock PDFs answers the last one cheaply.
